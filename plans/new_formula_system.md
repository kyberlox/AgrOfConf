# Архитектура: новая система расчёта формул

## Цель

Заменить громоздкую логику расчёта (класс `CodeParametr`, 1837 строк, в
`app/TableSearch/utils/code_mode.py`) на **простую библиотечную систему**:

- алгоритмы и валидаторы пишутся как **обычные Python‑функции** в файлах кода
  (не в БД);
- привязка параметра к функциям хранится в **JSON‑поле** в БД;
- внутри функции значения зависимых параметров получаются через контекст:
  `ctx.get("Параметр Б")`; если параметр не выбран — функция останавливается и
  в результат параметра возвращается просьба заполнить его;
- вычисления выполняются **асинхронно** (параллельно независимые формулы).

Старый `CodeParametr` сохраняется как **fallback** для существующих параметров,
у которых нет нового JSON‑конфига.

---

## Ключевые согласованные решения

1. **Новая система — основной механизм**; старый `CodeParametr` остаётся в коде
   и используется только как fallback для совместимости старых параметров.
2. **Конфигурация параметра — JSON‑поле** (гибкое), пример:
   ```json
   {
     "func": "count_A",
     "validate": "validate_nonzero",
     "type": "formula"
   }
   ```
   - `func` — имя функции расчёта из библиотеки алгоритмов;
   - `validate` — имя функции валидации из библиотеки валидаторов;
   - `type` — `"formula"` для расчётных параметров.
3. **Семантика `ctx.get(name)`** — требует значение. Если параметр не выбран,
   поднимается исключение `MissingParamError`, движок превращает его в сообщение
   `Заполните параметр "<имя>"`. Для опциональных зависимостей есть `ctx.get_opt(name)`,
   возвращающий `None`.

---

## Типы параметров (входные данные)

Тип ввода уже описывается полем `required_type` у `ParameterSchema`:

| `required_type` | Назначение |
|-----------------|-----------|
| `user_input`    | Пользователь вводит значение вручную (можно валидация) |
| `list`          | Выбор одного значения из предложенного списка |
| `select-input`  | Выбор из списка + ручной ввод |

Для всех типов можно указать функцию валидации (`validate`). Валидация может
зависеть от значений других параметров (контекст доступен).

## Структура новых файлов

```
app/formulas/
├── __init__.py        # экспорт публичного API
├── algorithms.py      # библиотека функций расчёта (одна или несколько)
├── validators.py      # библиотека функций валидации
├── registry.py        # реестры имён функций (для безопасного вызова по имени из БД)
└── engine.py          # FormulaContext, MissingParamError, движок вычислений
```

### `algorithms.py` — библиотека алгоритмов

Каждая функция — обычный Python‑деф: `def func_name(ctx) -> value`.
`value` может быть числом, строкой, списком, словарём — что ожидает фронтенд.

Пример (точно по ТЗ):

```python
from .engine import FormulaContext

def count_A(ctx: FormulaContext):
    B = ctx.get("параметр Б")   # не выбран -> MissingParamError -> просьба заполнить
    V = ctx.get("параметр В")
    G = ctx.get("параметр Г")
    if G != 0:
        return B * V / G
    else:
        return "Параметр Г определен неверно, значение не может быть равным '0'!"
```

> `ctx.get` возвращает «естественное» значение: числовые строки приводятся к
> `float`/`int`, остальное — как есть (строка/список). Для явного приведения
> доступны `ctx.num(name)` и `ctx.get_opt(name)`.

### `validators.py` — библиотека валидаторов

```python
from .engine import FormulaContext

def validate_nonzero(ctx: FormulaContext, value):
    if value is not None and value == 0:
        return "Значение не может быть равным 0"
    return None   # ошибок нет
```

Сигнатура: `def validator(ctx, value) -> str | None`. Возвращает текст ошибки
или `None`. Значение проверяется у того параметра, для которого задан валидатор.
Внутри валидатора доступен `ctx`, чтобы проверять другие параметры
(например, диапазон зависит от выбранного типа).

### `registry.py` — реестры

```python
from . import algorithms, validators

ALGORITHMS = {name: fn for name, fn in vars(algorithms).items()
              if callable(fn) and not name.startswith("_")}
VALIDATORS = {name: fn for name, fn in vars(validators).items()
              if callable(fn) and not name.startswith("_")}

def get_algorithm(name): ...
def get_validator(name): ...
```

Реестр строится автоматически из содержимого модулей. Имя функции из БД
сверяется с реестром — неизвестное имя даёт ошибку параметра (безопасность).

### `engine.py` — контекст и движок

```python
class MissingParamError(Exception):
    def __init__(self, param_name: str): ...

class FormulaContext:
    def __init__(self, selected, computed, db): ...
    def get(self, name): ...      # требует значение; иначе MissingParamError
    def get_opt(self, name): ...  # None, если нет
    def num(self, name): ...      # get + float()
    def require(self, name): ...  # alias get
```

Движок — функция разрешения зависимостей и асинхронного вычисления:

```python
async def compute_formulas(
    db,
    formula_params: list[dict],   # id, name, config {func, validate, type}
    selected: dict[str, value],   # выбранные значения (ввод пользователя + табличные)
    table_params: list[dict],     # вычисленные табличные параметры (для формата ответа)
) -> dict[name -> результат]
```

Алгоритм движка (итеративные проходы с `asyncio.gather`):

1. `computed = {}` — кэш значений формульных параметров.
2. В цикле (пока есть прогресс):
   - берём ещё не вычисленные формулы;
   - запускаем их параллельно через `asyncio.gather` (контекст использует
     `computed` для уже готовых формул);
   - если функция завершилась результатом — кладём в `computed`;
   - если поднят `MissingParamError` на **другую формулу** — откладываем её на
     следующий проход (зависимость);
   - если `MissingParamError` на **вводном/табличном параметре** — результат
     параметра = `Заполните параметр "<имя>"`, помечаем как «недостающий ввод».
3. Проходы повторяются, пока вычислены все вычислимые либо не осталось только
   недостающие вводы (защита от зацикливания при циклических зависимостях —
   лимит проходов).

Асинхронность даёт параллельность независимых формул; зависимые — выполняются
в последующих проходах. Функции алгоритмов синхронные (быстрые), поэтому вызов
идёт через `asyncio.to_thread` при необходимости блокирующих операций, либо
напрямую, если функция лёгкая.

## Модель БД

### `ParameterSchema` (`app/TablePakage/model/parameter_schema.py`)

Добавить колонку:

```python
formula_config = Column(JSON, nullable=True)   # {"func": "...", "validate": "...", "type": "formula"}
```

Существующие поля (`type`, `required_type`, `field_of_view`) остаются без изменений
для совместимости со старой системой (fallback).

### Миграция

Проект использует `Base.metadata.create_all`, которая **не добавляет колонки** в
существующую таблицу. Добавляется функция миграции, вызываемая при старте:

```python
async def ensure_formula_config_column(db):
    await db.execute(text(
        "ALTER TABLE parameter_schemas ADD COLUMN IF NOT EXISTS "
        "formula_config JSONB"
    ))
```

Вызывается в `startup_event` (после `create_tables`).

## Интеграция в `module_search`

Файл: `app/TableSearch/router/module_search.py` (функция `process_table_data`).

Сейчас формульные параметры считает `search_formula(...)` через `CodeParametr`.
Новый порядок:

1. Получить список формульных параметров продукта (`type='Formula'`).
2. Разделить их:
   - **новые** — у которых `param.formula_config` (dict) содержит `func`;
   - **старые** — остальные (передаются в существующий `search_formula` = fallback).
3. Новые вычислить движком `compute_formulas(...)`.
4. Объединить результаты и вернуть параметры в **прежнем формате**:
   ```python
   {
     "id", "name", "description", "table_name", "all_values",
     "response_value", "visibility", "required_type", "sort",
     # при ошибке:
     "error": "сообщение"
   }
   ```
   Для расчётных параметров `required_type='raschet'` сохраняется (фронт использует
   это значение в `Configurator.vue` для фильтра результатов).

Имя функции для параметра берётся из `formula_config["func"]`. Если имя не найдено
в `registry` — параметр получает `error` с описанием.

Формат запроса `/module_search/process_table_data` и ответа **не меняется**.

## Сохранение совместимости форматов

- Запрос фронта: `POST /module_search/process_table_data?product_id=X`, тело —
  `{имя_параметра: значение, priority?}` — **без изменений**.
- Ответ: массив параметров (поля выше) — **без изменений**.
- Табличный подбор (`get_table_params_from_sql`, `dm_search`) — **не затрагивается**.
- Старый `search_formula`/`CodeParametr` — работает как fallback.

## UI в админ‑карточке параметра

Файлы: `front/src/views/admin/product/Product.vue` (управление параметрами
продукта) и связанные модальные окна параметров.

Требуется добавить поля для расчётных параметров (`type='Formula'`):

- **Функция расчёта** — текстовое поле, значение = имя функции из `algorithms.py`
  (например `count_A`). Сохраняется в `formula_config["func"]`.
- **Функция валидации** — текстовое поле, значение = имя функции из
  `validators.py`. Сохраняется в `formula_config["validate"]`.

Опционально: выпадающие списки со списком доступных имён функций, получаемые с
бэкенда (эндпоинт `/formula_functions`, возвращающий ключи `registry.ALGORITHMS` и
`VALIDATORS`), чтобы исключить опечатки.

При сохранении параметра (POST/PUT `/api/parameters`) Pydantic‑схема должна
принимать `formula_config` (JSON) и передавать его в модель.

## Риски и ограничения

- **Циклические зависимости** между формулами — защита лимитом проходов.
- **Приведение типов** (`ctx.get`) может отличаться от ожидаемого — ввести явные
  хелперы `ctx.num`/`ctx.get_opt`, документировать.
- **Имя функции в БД** — только известные из реестра; неизвестное → ошибка параметра.
- Формулы выполняются на каждый запрос подбора (как и раньше); при росте числа
  параметров — добавить кэширование на сессию при необходимости.
